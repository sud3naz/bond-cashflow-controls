# Bond Cash Flow and Data Controls

A small, source-traceable analysis of scheduled coupon and principal payments for five USD-denominated, fixed-coupon Turkish domestic government bonds. Official instrument terms are separate from hypothetical portfolio holdings.

The project combines business requirements, SQL analysis, financial cash-flow calculations and explicit data-quality controls. It is an independent learning case, not a real institution's portfolio or a production investment system.

**[View the complete report in your browser — no download required](reports/README.md).** It shows the findings, chart, full payment schedule, assumptions and source links. The Excel workbook is optional.

![Cash flow report overview](reports/overview.png)

## Business question

Which gross coupon and principal payments are scheduled, how much remains after a fixed reporting date, and which invalid inputs should stop the report?

The assumed operations analyst needs a reliable payment calendar. A reviewer needs to trace rates and dates back to official disclosures, distinguish facts from holdings assumptions, and investigate validation messages before using the analysis.

## Reproduce the numerical analysis

Use Python 3.10 or newer. The analysis and tests use only the Python standard library, including SQLite. No API key, internet connection, paid data service or third-party Python package is required to run the included sample.

From this project directory:

```bash
python3 src/analyze.py
python3 -m unittest discover -s tests -v
```

The first command validates the inputs, creates an in-memory database, and writes `reports/analysis.json` plus four CSV tables. The database is not persisted. The second command runs the automated tests.

The numerical report is deterministic for the same inputs and reporting date. An input-content SHA-256 is included for comparison. If validation fails, the command exits with status 2 and writes an explicit invalid `analysis.json`; earlier CSV and workbook snapshots must not be used for that failed run.

## Excel report

Open [the portfolio workbook](reports/bond_cashflow_report.xlsx). It contains a summary, editable assumptions, payment-level formulas, official terms and sources, and terminal reconciliation checks. Native chart series are linked to formula cells.

Yellow nominal and reporting-date cells on `Assumptions` are editable. Changes recalculate the workbook's summaries and chart. Keep source terms and payment rows unchanged for this fixed five-instrument report. Missing or invalid nominal inputs are shown as unavailable rather than silently becoming zero.

The delivered workbook's default values were reconciled with `analysis.json`. The Python CLI **does not regenerate the workbook**. Workbook edits do not update JSON, and JSON edits do not automatically update Excel. To compare a new nominal/date scenario, use identical assumptions in both and rerun the Python analysis. Adding instruments requires updating the workbook structure as well as source data. Spreadsheet-engine calculation, input changes, renders and XLSX reimport were checked; native Microsoft Excel application testing is still pending.

## SQL and controls

Four tables separate sources, instrument terms, scheduled dates and assumed positions. Seven [SQL queries](sql/) cover the source payment schedule, payment-month totals, the next 90 days, a continuous monthly calendar, complete/remaining totals, nominal maturity concentration and overlapping 30/90/365-day horizons.

The validation layer reports rule, severity, record path and message. R01–R09 cover invalid rates and nominals, duplicates, dates, relationships, incomplete coupon sequences, final maturity payments, scope and provenance. Invalid source inputs stop normal analysis. Zero is distinct from missing. Zero total nominal makes a concentration share undefined, not zero percent.

Nine intentionally invalid cases in [quality_demo_cases.json](data/quality_demo_cases.json) exercise the controls on separate deep copies; they are never mixed with the source facts. The default sourced inputs have no detected validation issues. That is not a claim that all possible data errors can be detected automatically.

## Limitations

The project assumes constant nominal holdings from issue to maturity and scheduled gross payments only. It has no purchase prices, trade history, verified receipts, tax, fees, FX conversion, accrued interest, current market valuation, yield calculation, credit scoring, optimization or investment recommendations. A past scheduled payment must not be treated as proof of collection.

The control and SQL code are intentionally simple and the dataset is small. Financial value comes from traceable inputs, correct definitions and reproducible calculations rather than a large-data or advanced-model claim.
